=== (d) Desync banner — safe method ===
1. Unregistered via the popover's own "Launch at Login" toggle (VO-activated) — confirmed
   via app debug log: refreshLaunchAtLoginStatus status=0 userIntended=false desynced=false
   (still in sync, both flipped off together).
2. Forced desync: `defaults write com.slenbder.pastequeue userEnabledLaunchAtLogin -bool true`
3. IMPORTANT FINDING: reopening the popover (via AXPress `click`, and separately via a real
   synthetic click that verifiably transferred VO focus) did NOT retrigger
   refreshLaunchAtLoginStatus. It only fired ~3 times total, all within the first 35 seconds
   after app launch. Every subsequent popover open in the same running process — including
   several confirmed-focused opens during the row/delete tests — produced NO new
   refreshLaunchAtLoginStatus log line. This contradicts the assumed design ("recomputed on
   every popover .onAppear"); in practice it looks like SwiftUI's .onAppear on the popover's
   root view only fires on the view's first materialization for the lifetime of the popover's
   NSHostingController, not on every subsequent show(). Net effect: a real user who disables
   Launch at Login in System Settings while PasteQueue has already been running for a while
   would likely never see this banner, no matter how many times they reopen the popover,
   until they quit and relaunch the app.
4. Verified the "app launch" pathway works correctly: quit + relaunched PasteQueue via Xcode
